1. Data and Schema Analysis

1.1 File Format and Encoding
  • Full source file: 215885-0-contaminacion-ruido.csv, about 44.7 MB; the committed extract is csv/contaminacion_acustica.csv (11 columns).
  • Encoding: ISO-8859-1 (Latin-1), not UTF-8. The header Estación;Año;Mes;Día is broken if read as UTF-8.
  • Separator: semicolon (;). Line endings: CRLF.
  • Decimal mark: comma (68,9). Values have at most one decimal; whole values have none (68).
  • Missing values: the string N/D (no disponible).
  • Update: daily, except weekends and public holidays. The last day in the file is 04/10/2026.

The official station schema identifies geographic coordinates as WGS84 and projected X/Y as ETRS89. Use ETRS89 / UTM 30N (EPSG:25830) for metre-based distance calculations, transforming to WGS84 (EPSG:4326) for map latitude/longitude. All 31 geographic coordinate pairs contain an extra dot in the fractional part. For the observed pattern, preserve the sign and first decimal point and concatenate the following digit groups: -3.691.509 → -3.691509 and 40.409.121 → 40.409121. Validate the pattern and geographic bounds, and check against the transformed X/Y pair before using a repaired value. Other unexpected formats require inspection.

There are 18 raw district spellings and 17 after trimming, plus 30 distinct neighbourhood names. For station district links, trim, uppercase, remove accents for comparison and normalize spaces around hyphens. Neighbourhood names need a separate checked mapping within their district: abbreviations such as Pilar and the spelling Quitana do not automatically match census labels. Geographic names and the verified district reconciliation are analysed for future enrichment. The current lightweight station model represents identifier, name and coordinates; station district/neighbourhood links, location description, altitude and registration date are outside its current scope.

1.6 Terraces File (200085)

File csv/terrazas_hosteleria.csv (copy of the portal file 200085-6-censo-locales.csv, the "Terrazas" resource of the dataset): 6,594 rows (one per terrace), 117 columns, about 5.2 MB, data loaded on 04/10/2026 (column fx_carga).

  • Format: UTF-8 with BOM (different from the two noise files, which are ISO-8859-1), semicolon separator and CRLF line endings. Headers and text values are quoted; numeric and boolean values are generally unquoted.
  • Decimal mark: point (16.70), not comma. Booleans are written True / False.
  • Key: id_terraza is unique (no duplicates). One premise (id_local) can have several terraces (6,438 premises for 6,594 terraces).
  • Missing values and dates: empty strings or whitespace-only fields mean unavailable/not applicable; numerical zero remains a source value, except the invalid coordinate sentinel (0,0). S/R is a missing business-name marker. fx_carga uses dd/mm/yyyy; Fecha_confir_ult_decreto_resol contains timestamps such as 2014-04-07 09:27:35.943, recording an administrative resolution rather than a historical opening date.
  • Suffixes: columns ending in _es refer to the seasonal period and columns ending in _ra to the rest of the year. According to the official terrace schema, LJ covers Sunday–Thursday and VS covers Friday, Saturday and holiday eves. Hours use HH:mm:ss (target datatype xsd:time if later modelled).

The following inventory describes relevant source fields. The lightweight ontology represents terrace ID, location, district and neighbourhood, supporting the application's count of registered terraces near stations. Access type determines which coordinates can be used. Business names, administrative status, seasonal periods, capacity, surface and schedules are analysed as context but are outside the current model. Furniture, heaters, awnings, planning zones and the remaining administrative fields are also excluded because the current application requires terrace counts rather than those attributes.

The official schema states that current terrace coordinates use ETRS89; ED50 applied before 15 September 2017. This 2026 snapshot therefore uses EPSG:25830, matching the station X/Y system. Use coordenada_x/y_local only for street-access premises (id_tipo_acceso_local=1) that are not in Baja, and coordenada_x/y_agrupacion for grouped premises (id_tipo_acceso_local=0). Require both coordinates to be present and nonzero and inspect values outside the Madrid extent. Local-coordinate values supplied for other access types are invalid according to the source documentation.

With these checks, 6,443 street-access terraces and 91 grouped terraces have usable approximate locations: 6,534 located terraces and 60 without a usable location. Of the 112 zero local-coordinate pairs, 53 can be recovered through nonzero grouping coordinates. Conversely, 39 nonzero local-coordinate pairs belong to 38 grouped terraces and one interior premise and must not be accepted as local entrance coordinates. Unlocated terraces retain their identifiers and geographic area links but are excluded from distance counts. A premise or grouping entrance is a location proxy, not a measured terrace centroid or polygon; 1,476 rows have a terrace address identifier different from the building address identifier, so counts near a radius boundary have positional uncertainty.

Schedules provide context for the night-time question: in the seasonal period, 94.7% of LJ closing times and 99.0% of VS closing times lie between 00:00 and 02:30, inside the noise N period (23–7h). These figures describe authorized schedules in the snapshot, not verified actual operation.

Temporal limitation: all terrace rows were loaded on 04/10/2026, whereas submitted noise measurements span 2020–2026. This single snapshot cannot identify which terraces existed or operated, or their capacities and hours, on each historical noise date. A correlation using historical noise compares it with the 2026 registered-terrace distribution; it must be presented with that limitation. A study of contemporaneous activity would require historical terrace inventories and verified dates. The current model counts registered terraces, including temporarily suspended registrations, and does not infer actual activity from capacity or opening hours.

Data Quality Issues Found

  • Different station codes: the measurements use integers (2), the catalog uses RF-02. Mapping: n → RF- + n padded to two digits.
  • Full-history stations without catalog entries: codes 7, 9, 21, 22 and 23 (2009–2010) have no description in the current catalog. They are absent from the submitted extract, whose 31 station codes all match.
  • Full-history outliers: 4 LAeq rows exceed 100 dB(A) (stations 18 and 13, April and August 2007, up to 140.2) and 39 fall below 35 dB(A). Retain source values and flag them for inspection. The extract has no LAeq above 100 and 19 below 35.
  • Percentile issues: the full history has 4 rows with a zero percentile and 4,262 rows with inconsistent percentile order (0.6% of rows with percentiles). The committed extract has 4 and 4,198 respectively, as quantified in Section 1.4a.
  • Catalog formatting and history: apply the coordinate repair and district normalization in Section 1.5. The spelling Quitana requires a checked neighbourhood mapping. RF-01's FECHA ALTA is 07/03/2011 although station code 1 has older observations; the source documents station relocations, and this field must not be assumed to date the first historical observation or prove that all older measurements used today's location.
  • Terrace location quality: use the access-type and grouping-coordinate rules in Section 1.6; 6,534 rows have usable entrance proxies, and 60 remain outside distance counts.

3. Resource Naming Strategy

3.1 Domain and URI Form

We adopt https://madridnoise.linkeddata.es as the designed base URI for our Madrid noise and terraces dataset. This keeps the naming strategy consistent with the dataset identifier in Section 2.4 and uses a project domain rather than the namespace generated by default in Protégé. All identifiers are absolute HTTPS URIs.

Publication status: this is the namespace selected for the ontology and the RDF data to be generated. DNS delegation, permission to use the subdomain, HTTPS hosting and the HTTP routes described below must be arranged before publication. The assignment defines their intended behaviour; it does not claim that these URLs currently resolve.

PurposeURI or pattern
Ontology identifier and describing documenthttps://madridnoise.linkeddata.es/ontology
Ontology term namespacehttps://madridnoise.linkeddata.es/ontology#
Data entity identifiershttps://madridnoise.linkeddata.es/resource/{entity-type}/{identifier}

HTML descriptions of data entitieshttps://madridnoise.linkeddata.es/page/{entity-type}/{identifier}

Braces in the patterns denote placeholders and are not part of an actual URI. Entity identifiers have no file extensions, query parameters or trailing slash. Paths and identifiers are case-sensitive. The /page/ and /data/ paths identify describing documents; the /resource/ paths identify the things described.

3.2 Ontology Terms and Prefixes

The ontology uses hash URIs: a locally defined class or property is named by appending its local name to https://madridnoise.linkeddata.es/ontology#. The implemented classes use English PascalCase: NoiseMonitoringStation, DailyNoiseObservation, DayPeriod, Terrace, District and Neighbourhood. Properties start with a lowercase letter, with lowerCamelCase for multiword names, such as recordedAt, forPeriod and observationDate. Section 4 documents the final terms, domains, ranges and source-field mappings.

A property URI is independent of the class using it: https://madridnoise.linkeddata.es/ontology#recordedAt, rather than a property nested under a class URI. Individual URIs are also independent of class URIs: https://madridnoise.linkeddata.es/resource/station/RF-02, rather than an identifier appended to .../ontology#NoiseMonitoringStation. Ontology terms and individuals therefore occupy different paths.

The following prefixes identify the same namespaces wherever they are used in the ontology and its sample instantiation:

@prefix mn:            <https://madridnoise.linkeddata.es/ontology#> .
@prefix station:       <https://madridnoise.linkeddata.es/resource/station/> .
@prefix observation:   <https://madridnoise.linkeddata.es/resource/observation/> .
@prefix terrace:       <https://madridnoise.linkeddata.es/resource/terrace/> .
@prefix district:      <https://madridnoise.linkeddata.es/resource/district/> .
@prefix neighbourhood: <https://madridnoise.linkeddata.es/resource/neighbourhood/> .

dataset: names our generated datasets; sourceDataset: names the official source datasets. For example, dataset:daily-noise and sourceDataset:215885-0-contaminacion-ruido have different expanded URIs. Standard vocabulary prefixes retain their authoritative namespaces: owl: = http://www.w3.org/2002/07/owl#, rdf: = http://www.w3.org/1999/02/22-rdf-syntax-ns#, rdfs: = http://www.w3.org/2000/01/rdf-schema#, xsd: = http://www.w3.org/2001/XMLSchema#, dcterms: = http://purl.org/dc/terms/, dcat: = http://www.w3.org/ns/dcat#, sosa: = http://www.w3.org/ns/sosa/ and geo: = http://www.w3.org/2003/01/geo/wgs84_pos#.

Prefix names are abbreviations only: the expanded URI determines identity. Reused classes and properties retain their original vocabulary URIs; the mn: namespace is for terms defined by our group. Ontology labels and comments will consistently use English with @en; Spanish station and place names remain source data values.

3.4 Normalization, Missing Identifiers and Collisions
  • Source keys: trim surrounding whitespace, parse integer identifiers, and apply the canonical formats above. Validate date components as a real calendar date and normalize period codes to uppercase. Keep historical station codes even if the current catalog does not describe those stations.
  • Geographic reconciliation: match station place names to census codes within their district. Whitespace, case and accents can be normalized for comparison, but the resulting URI uses the verified numeric code. Abbreviations and spelling differences require an explicit checked mapping. If a match is absent or ambiguous, retain the source name as a literal and defer the coded relationship; do not invent a geographic identifier.
  • URI-safe characters: the selected keys use ASCII digits, letters and hyphens, so they require no escaping. Future identifiers containing other characters must be encoded as UTF-8 and percent-encoded within their own path segment; reserved characters such as /, # and ? must not become separators. Do not derive identifiers by deleting accents from names.
  • Missing keys: do not mint a shared unknown, empty or N/D identifier, or substitute the CSV row number. Rows without a valid required key must be reported and deferred until their identity is resolved. Missing measurement values do not invalidate an otherwise valid observation key and must not form part of its URI.
  • Uniqueness: check uniqueness after normalization. Repeated rows with the same source key describe the same entity; conflicting values must be reviewed rather than resolved by adding an arbitrary suffix. Different entity types cannot collide because their paths differ. If a future source uses overlapping identifiers for different entities of the same type, define a source-qualified pattern before minting them.

The publication design offers HTML for people and Turtle for RDF clients. Ontology terms use hash URIs because the lightweight vocabulary can be described in one document. Data entities use slash URIs and 303 See Other redirects to their describing documents. This follows the distinction between resources and descriptions in W3C hash URIs and W3C 303 URIs.

The same redirect pattern applies to observations, terraces, districts, neighbourhoods and periods. Dataset identifiers use /page/dataset/{dataset-name} and /data/dataset/{dataset-name} for their HTML and RDF metadata descriptions. The latter describes the dataset; it is not the URI of a complete data download.

The server will select a supported representation using the request's Accept header and quality preferences. Missing Accept or an unrestricted wildcard defaults to HTML; ties favour HTML. If neither HTML nor Turtle is acceptable, return 406 Not Acceptable. Responses selected by negotiation, including redirects, include Vary: Accept. A final HTML document has Content-Type: text/html; charset=utf-8; a final RDF document has Content-Type: text/turtle; charset=utf-8. Requests for identifiers absent from the published data return 404 Not Found.

For example, an RDF client requesting a station would receive this redirect before retrieving its description:

GET /resource/station/RF-02 HTTP/1.1
Host: madridnoise.linkeddata.es
Accept: text/turtle

HTTP/1.1 303 See Other
Location: https://madridnoise.linkeddata.es/data/station/RF-02
Vary: Accept

The describing RDF document makes assertions about https://madridnoise.linkeddata.es/resource/station/RF-02, not about .../data/station/RF-02 as though that document were the station. All responses above are the agreed design for the later publication stage, not implemented hosting in this assignment. See W3C content negotiation.

3.6 Persistence and External Resources

Once minted, an identifier is retained across CSV reorderings, added records, corrected labels, corrected measurements and changes in implementation. A corrected value for the same station/date/period updates the existing observation; a genuinely different observation key identifies a different observation. Retired stations retain their identifiers and available historical descriptions. Ontology or dataset release dates may be recorded in metadata without inserting a release version into every term or entity URI.

Ontology terms must not be repurposed for incompatible meanings. New terms receive new local names; deprecated terms keep their original identifiers. If the publication infrastructure changes, preserve the public base and routes or maintain redirects and document any unavoidable migration.

Links to external entities and reused vocabularies keep the external provider's URI unchanged. Districts and neighbourhoods are intended as geographic linking resources for later assignments. Identity links will be added only after verification; a similar name or nearby coordinates alone do not establish identity. Our local identifier remains stable when an external link is added.

The separation of vocabulary, entity and document paths and the use of source keys follow the W3C URI design principles and URI persistence guidance.
