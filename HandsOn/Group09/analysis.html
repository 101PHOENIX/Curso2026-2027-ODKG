Dataset Analysis, License Analysis and Resource Naming Strategy

1. Analyze the Dataset

1.1 Dataset description

The dataset used in this project is "Aparcamientos públicos municipales (rotacionales). Histórico de ocupación", published by the Ayuntamiento de Madrid, from Jan 2019 to August 2026. It contains monthly information about the occupancy of municipal public car parks that operate as rotational or mixed-use car parks.

The information is supplied by the companies responsible for managing the car parks. The dataset is provided as yearly CSV files. The available files cover the years 2019 to 2026, with the 2026 data being partial because the year is still in progress. For the detailed analysis below, we will use the year 2025 dataset.

There is also a related dataset, "Aparcamientos municipales. Número de plazas", which contains information about the municipal car parks, including their locations. This dataset can be useful for adding more information to the occupancy data.

1.2 Dataset size

The 2025 file contains 606 data rows, excluding an empty line at the end of the file. It contain 12 columns and information about 52 car parks located in 12 different districts of Madrid.

  • Time period: January to December 2025
  • Car parks: 52
  • Districts: 12
  • Total capacity: 16,238 parking spaces
  • Columns: 12

1.3 Schema

The main columns in the dataset are:

Column Type Description
AÑO Integer Year of the observation.
MES Integer Month of the observation, from 1 to 12.
NOMBRE DEL APARCAMIENTO String Name of the car park.
CÓDIDO PAR Integer PAR code identifying the car park. The column name contains a typo in the original source.
TIPO String Type of car park. The values in the analysed file are ROT.
NUM PLAZAS Integer Number of parking spaces.
CÓDIGO DISTRITO Integer Code of the Madrid district.
DISTRITO String Name of the Madrid district.
Días Cálculo Integer Number of days used to calculate the monthly values.
Vehículos día (media) Integer Average number of vehicles per day.
Ocupación (%) String Occupancy percentage for the calculation period, stored using a comma as the decimal separator and including the percent sign.
Ocupación 9h-21h (%) String Occupancy percentage between 09:00 and 21:00.

The occupancy columns are stored as text in the original CSV, for example 38,3%. For the RDF representation, the percentage sign and comma decimal separator will need to be converted so that the value can be represented as a decimal.

1.4 What does one row represent?

Each row represents the occupancy information for one car park during one month. Therefore, an observation can be identified using the car park code, year and month. For example, the combination 5000 + 2025 + 01 represents the January 2025 occupancy information for the Almagro car park.

This structure is also useful when creating identifiers for the monthly occupancy records. A combination of the car park code, year and month provides a stable way to distinguish one monthly observation from another.

1.5 Data quality and preprocessing

Several characteristics of the source data were considered before using the dataset.

  • Empty line: the 2025 file contains an empty trailing line, which is ignored during the analysis.
  • Column name: the source contains the header CÓDIDO PAR. The original spelling is preserved when describing the source, while the PAR code itself is used as the identifier.
  • Occupancy percentages: values such as 38,3% are stored as strings and should be converted to decimal values for RDF.
  • District names: some district values contain trailing spaces. Districts should therefore be identified primarily using their district code.
  • Accents: Spanish accents and names are kept when representing the original values, but they are not used to construct URIs.
  • Missing months: not every car park necessarily has an observation for every month. Missing observations should not automatically be treated as zero.
  • Partial calculation periods: some observations are calculated using fewer days than a complete month. The Días Cálculo value is therefore preserved.
  • Occupancy above 100%: at least one value is above 100%. For example, Almagro has an occupancy of 126.2% in August 2025. This value is kept because a rotational car park can serve more vehicles during a day than the number of physical parking spaces.
  • Zero average vehicles: four rows have a value of zero for average daily vehicles. These rows are kept rather than removed.
  • Car park type: the analysed rows contain ROT. The catalogue describes Plaza Mayor and Montalbán as mixed-use car parks, so this difference is documented rather than silently changed.

1.6 Combining the yearly files

The yearly files can be combined after checking that they follow the same general structre. The 2026 file is partial and should therefore be treated differently from complete years.

A monthly observation can be identified by combining the PAR code, year and month. The PAR code is particularly useful because it provides a more stable identifier for a car park than its name, which may contain accents, spaces, or could change over time.

The dataset is also updated monthly, so the process used to generate the RDF data should be repeatable. New monthly observations can be added without changing the identifiers of existing car parks.

1.7 Possible links to other datasets

The PAR code can be used to connect the occupancy dataset with the companion municipal parking dataset containing information such as the location of the car parks.

Districts can also be connected to external resources representing Madrid's administrative areas. These links would connect one entity to another entity rather than simply adding external information as a literal value.

2. Analyze the License

2.1 Publisher and rightsholder

The dataset is published by the Ayuntamiento de Madrid. The municipality is therefore identified as the publisher/rightsholder of the source dataset in the project documentation.

2.2 License of the source dataset

The source dataset is published under the Creative Commons Attribution 4.0 International (CC BY 4.0) license.

This license allows the data to be reused, copied, redistributed and adapted, including for commercial purposes, provided that the required attribution is given. When the data is modified, the changes should also be indicated.

The main requirements when reusing the dataset are therefore:

  • Give appropriate attribution to the source.
  • Provide a link to the license.
  • Indicate if changes were made to the original data.

2.3 License for the generated dataset

For the dataset generated in this project, we propose using the same CC BY 4.0 license. This allows the resulting dataset to remain open and reusable while requiring users to provide appropriate attribution.

The generted dataset should include attribution to the Ayuntamiento de Madrid and should make clear that the data has been transformed as part of this project. The license and source information can also be represented in machine-readable form using metadata such as the dataset's license, source and publisher.

3. Define a Resource Naming Strategy

3.1 Base domain

The project uses the following domain as a placeholder: 

https://parking-madrid.example.org/
Important: example.org is only a placeholder and should be replaced with the real domain that will be used when the dataset is published.

HTTPS is used as the URI scheme. The strategy separates the URIs used for the ontology from the URIs used for the individual resources represented by the data.

3.2 URI structure

A different path is used for the ontology and for individual resources. This makes it easy to distinguish the concepts defined by the project from the actual resources represented in the dataset.

Ontology:

https://parking-madrid.example.org/ontology#

Car parks:

https://parking-madrid.example.org/resource/parking/{parCode}

Districts:

https://parking-madrid.example.org/resource/district/{districtCode}

Monthly occupancy observations:

https://parking-madrid.example.org/resource/occupancy/{parCode}-{yyyy}-{mm}

Datasets:

https://parking-madrid.example.org/resource/dataset/{name}

3.3 Naming rules

  • Car parks: use the PAR code rather than the car park name. For example, PAR code 5000 becomes /resource/parking/5000.
  • Districts: use the district code rather than the district name.
  • Occupancy observations: use the PAR code, year and month. This makes each monthly observation distinguishable.
  • Ontology terms: use the /ontology# namespace.
  • Individuals: use the /resource/ path.
  • Classes: use UpperCamelCase, for example ParkingFacility.
  • Properties: use lowerCamelCase, for example hasName or locatedInDistrict.
  • Avoid spaces, accents and special characters in URIs.
  • Do not use the human-readable name of a car park as its main identifier. Names are less suitable because they can contain spaces and accents and may change over time.
  • Property URIs are defined directly under the ontology namespace rather than being placed underneath the URI of a particular class.

3.4 Examples

Using the proposed strategy, the Almagro car park with PAR code 5000 would have: 

https://parking-madrid.example.org/resource/parking/5000

District 7 would have: 

https://parking-madrid.example.org/resource/district/7

The January 2025 occupancy observation for PAR code 5000 would have: 

https://parking-madrid.example.org/resource/occupancy/5000-2025-01

An ontology class would use the ontology namespace, for example: 

https://parking-madrid.example.org/ontology#ParkingFacility

An ontology property would also use the ontology namespace: 

https://parking-madrid.example.org/ontology#locatedInDistrict

This naming strategy provides stable and predictable identifiers for the resources in the dataset while keeping ontology terms and individual data resources clearly separated.
